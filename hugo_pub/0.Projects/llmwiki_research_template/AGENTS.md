# AGENTS.md

이 파일은 이 위키에서 일하는 모든 AI 에이전트(Claude Code, Gemini CLI, Codex, Cursor 등)가 따르는 규칙이다.
작업을 시작하기 전에 이 파일 전체와 `wiki/index.md`를 먼저 읽는다.

이 템플릿은 **자료 분석·문서 작성용**이다. 참고자료를 모아 정리·분석하고, 그 결과로 보고서·요약·변환 문서 같은 결과물을 만든다.
(코드를 개발하는 프로젝트는 `llmwiki_template`을 쓴다.)

---

## 0. 프로젝트 설정

> 새 프로젝트에 이 템플릿을 복사하면 이 섹션만 채운다.

- **프로젝트 이름**: (예: my_resume)
- **주제/목적**: (이 위키가 다루는 내용과 만들 결과물을 한두 문장으로)
- **주요 결과물 형식**: (예: DOCX, PDF, Markdown)
- **결과물 독자**: (예: 채용 담당자, 팀장, 나)
- **위키 언어**: 한국어
- **민감 정보**: (예: 연락처·주민번호는 결과물에만 넣고 위키에는 적지 않음 / 해당 없음)
- **문서 변환 도구**: (예: 에이전트 내장 기능, pandoc — 없으면 "에이전트에 맡김")

## 1. 폴더 구조

```
raw/                원본 자료 — 추가만 가능, 수정/삭제 금지
  sources/          참고자료: PDF, 기사, 문서, 메모, 기존 결과물
  assets/           양식 파일, 이미지, 첨부파일

wiki/               에이전트가 쓰고 고치는 지식 페이지
  index.md          전체 목차 (진입점)
  log.md            작업 기록 (추가만)
  overview.md       프로젝트 요약, 현재 상태
  sources/          자료별 요약 — raw/sources와 1:1
  concepts/         개념, 용어, 주제, 기술
  entities/         사람, 조직, 회사, 프로젝트, 제품 등 고유한 대상
  analysis/         여러 자료를 묶은 비교, 분석, 종합
  queries/          질문과 답 정리
  decisions/        분석 기준, 분류 방식, 작성 방침 결정 (누적)

outputs/            최종 결과물 — 결과물 하나당 폴더 하나
  YYYY-MM-이름/
    brief.md        요청 내용: 목적, 독자, 형식, 분량, 참고 양식
    outline.md      목차와 각 부분에 쓸 근거
    draft-v1.md     초안 (고칠 때마다 v2, v3 …)
    review-v1.md    검토 결과: 문장별 근거 대조
    final-v1.docx   최종본 (형식은 brief 기준)

templates/          문서 양식 — 새 문서는 반드시 여기서 복사해서 시작
```

## 2. 핵심 원칙

1. **원본과 정리를 나눈다.** `raw/`의 파일은 사람과 에이전트 모두 추가할 수 있지만, 한 번 들어간 파일은 누구도 수정하거나 삭제하지 않는다. 요약, 해석, 결론은 `wiki/`에, 결과물은 `outputs/`에 쓴다.
2. **근거 없이 쓰지 않는다.** 위키와 결과물의 모든 사실(특히 **숫자, 날짜, 기간, 이름, 성과**)에는 출처를 단다. 원본에 없는 내용을 지어내거나 부풀리지 않는다. 추정이 필요하면 "추정"이라고 표시하고 사용자에게 확인한다.
3. **지식과 결과물을 나눈다.** `wiki/`는 여러 결과물이 함께 쓰는 지식 창고다. 결과물마다 다르게 표현하는 것은 `outputs/`에서만 한다. 결과물에서 새로 알게 된 사실은 `wiki/`에도 반영한다.
4. **단계를 섞지 않는다.** 결과물은 ① 요청 → ② 개요 → ③ 초안 → ④ 검토 → ⑤ 최종 순서로 만들고, 각 단계가 끝나면 사용자 승인 후 다음 단계로 넘어간다.
5. **민감 정보를 조심한다.** "0. 프로젝트 설정"의 민감 정보 규칙을 따른다. 위키 페이지에는 필요한 만큼만 적는다.

## 3. 작업 흐름

### 3.1 자료 넣기 (Ingest)

`raw/`에 새 자료가 들어오거나 사용자가 자료를 주면:

1. 원본이 `raw/`에 없으면 알맞은 하위 폴더에 저장한다. (웹 자료는 본문을 Markdown으로 저장하고 출처 URL과 수집일을 맨 위에 적는다.)
2. `templates/source.md`로 `wiki/sources/`에 요약 페이지를 만든다. (원본 1개 = 요약 1개)
3. 등장하는 개념은 `wiki/concepts/`, 사람·조직·프로젝트 등은 `wiki/entities/` 페이지를 만들거나 갱신한다.
4. 기존 페이지와 모순되는 내용이 있으면 양쪽 페이지에 표시하고 사용자에게 알린다.
5. `wiki/index.md`와 `wiki/log.md`를 갱신한다.

자료가 많으면 한 번에 다 하지 말고 몇 개씩 나눠서 하고, 중간에 사용자에게 진행 상황을 알린다.

### 3.2 질문·분석하기 (Query)

1. `wiki/index.md`를 먼저 읽고 관련 페이지를 찾아 답한다. 위키에 없으면 `raw/`를 확인한다.
2. 답변에는 참고한 페이지와 원본 경로를 밝힌다.
3. 답변이 다시 쓸 만하면 **"위키에 저장할까요?"라고 묻고**, 승인받으면 짧은 답은 `queries/`, 여러 자료를 묶은 비교·분석은 `analysis/`에 저장한다.
4. 분석 기준이나 작성 방침이 정해지면 `decisions/`에 남긴다. (사용자 승인 후)
5. `wiki/log.md`에 기록한다.

### 3.3 점검하기 (Lint)

사용자가 요청하면 다음을 찾아 보고하고, 승인받은 항목만 고친다.

- 끊긴 `[[링크]]`, 어디에서도 링크되지 않은 페이지, `index.md`에 빠진 페이지
- 페이지끼리 모순되는 내용, 오래된 내용
- 출처가 없는 사실, 요약 페이지가 없는 원본
- 결과물(`outputs/`)과 위키 내용이 어긋난 곳

### 3.4 결과물 만들기 (① 요청 → ⑤ 최종)

| 단계 | 하는 일 | 출력 | 다음 단계로 가는 조건 |
|---|---|---|---|
| ① 요청 | 목적, 독자, 형식, 분량, 참고 양식을 정리. 모르는 것은 묻는다 | `outputs/YYYY-MM-이름/brief.md` | 사용자 승인 |
| ② 개요 | 목차와 각 부분에 쓸 위키 페이지·원본을 정한다. 근거가 부족한 부분을 표시 | `outline.md` | 사용자 승인 |
| ③ 초안 | 개요대로 쓴다. 문장마다 근거를 달 수 있어야 한다 | `draft-v1.md` | 초안 완성 |
| ④ 검토 | 초안의 사실을 하나씩 원본과 대조한다. 근거 없음·불일치·과장은 고치거나 표시 | `review-v1.md` | 문제 항목 처리 + 사용자 승인 |
| ⑤ 최종 | brief의 형식으로 변환. 참고 양식이 있으면 모양을 맞춘다 | `final-v1.<형식>` | 사용자 확인 |

- **③ 초안은 ① 요청과 ② 개요가 승인되기 전에 쓰지 않는다.**
- 검토에서 문제가 나오면 결과를 있는 그대로 `review` 파일에 기록한다. 문제를 숨기지 않는다.
- 참고 양식(`raw/assets/`)이 있으면 ②에서 양식의 항목 구성을 개요에 반영하고, ⑤에서 모양을 맞춘다.

### 3.5 결과물 고치기·새로 만들기

- **같은 결과물을 고칠 때**: 이전 파일은 그대로 두고 `draft-v2.md`, `review-v2.md`, `final-v2.docx`처럼 번호를 올린다. `brief.md`에 바뀐 요청을 날짜와 함께 덧붙인다.
- **비슷한 결과물을 새로 만들 때** (예: 다른 회사에 낼 이력서): 새 폴더를 만들고 ①부터 시작한다. 이전 결과물은 참고만 하고, 사실은 `wiki/`에서 가져온다.

## 4. 작성 규칙

### 4.1 파일명

- kebab-case를 쓴다. 한글도 쓸 수 있다. (예: `project-alpha.md`, `데이터-분석.md`)
- 결정 기록: `D-0001-제목.md` (번호는 계속 증가)
- 질문 정리: `YYYY-MM-DD-제목.md`
- 결과물 폴더: `outputs/YYYY-MM-이름/`

### 4.2 Frontmatter

모든 위키 페이지와 결과물의 md 파일은 맨 위에 frontmatter를 둔다.

```yaml
---
type: source | concept | entity | analysis | query | decision | brief | outline | draft | review
title: 페이지 제목
status: draft | in-progress | done      # 결과물 문서와 결정 기록만
tags: []
sources: []                             # raw/ 경로 또는 URL
related:                                # 위키 링크는 따옴표로 감싼 목록
  - "[[연결 페이지]]"
created: YYYY-MM-DD
updated: YYYY-MM-DD
---
```

frontmatter는 Obsidian 속성(YAML)으로 읽힌다. 다음을 지킨다.
- 위키 링크는 **따옴표로 감싼 목록**으로 쓴다: `related:` 다음 줄에 `  - "[[페이지]]"`. `related: [[a]], [[b]]`처럼 쓰면 링크가 깨진다.
- `{{title}}`, `{{date}}` 같은 템플릿 자리표시는 따옴표로 감싼다: `title: "{{title}}"`.
- `:`, `#`, `[`, `{`로 시작하거나 그런 글자를 포함한 값은 따옴표로 감싼다.

### 4.3 링크와 근거 표시

- 위키 페이지끼리는 `[[페이지명]]`으로 연결한다. 새 페이지는 최소 1개 이상의 기존 페이지에서 링크되게 한다.
- 본문의 사실 뒤에는 근거를 단다: `… 30% 줄였다. ([[project-alpha]], raw/sources/2024-평가서.pdf p.3)`
- 결과물 최종본(DOCX, PDF)에는 근거 표시를 넣지 않는다. 근거는 `draft`와 `review`에 남긴다.

### 4.4 log.md 형식

새 기록은 맨 아래에 추가하고, 기존 기록은 고치지 않는다.

```markdown
## [YYYY-MM-DD] 종류 | 제목
- 변경: 만들거나 고친 페이지·파일
- 메모: (선택)
```

종류: `ingest`, `query`, `analysis`, `lint`, `brief`, `outline`, `draft`, `review`, `final`, `decision`

## 5. 멈추고 사용자에게 물어야 할 때

- 단계를 넘어갈 때 (승인)
- 요청(목적, 독자, 형식)이 모호할 때
- 근거 자료가 부족하거나 자료끼리 충돌할 때
- 숫자, 날짜, 성과를 추정해야 할 때 (지어내지 않는다)
- 민감 정보를 위키나 결과물에 넣어야 할지 애매할 때
- `raw/`의 파일을 수정하거나 삭제해야 할 것 같을 때 (원칙적으로 금지)
- 위키 구조(폴더, 규칙)를 바꿔야 할 때
